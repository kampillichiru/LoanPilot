## POC 1: Talk to a local LLM from Java
- **What I built:** Spring Boot 4.1 + Spring AI 2.0 + Ollama (`qwen2.5:7b`) with `GET/POST /api/ask`. The system prompt is loaded from a versioned file (`prompts/banking-assistant-v1.st`), temperature and system prompt can be overridden per request, and every response returns model, prompt version, temperature, prompt/completion tokens and latency. A unit test with a fake `ChatModel` checks what Spring AI sends, with no Ollama needed.
- **What I learned:** Temperature reshapes token probabilities; it does not make output deterministic. The model still samples, so the same question at 0.2 gave two differently worded answers (172 prompt tokens both times, 79 vs 72 completion tokens). The system prompt is just more tokens in the context: it steers the model, it doesn't enforce anything.
- **What surprised me / what broke:** Asked "What is FOIR?", the model said "Fixed Operational Interest Rate" twice, confidently. That's wrong: it is Fixed Obligation to Income Ratio (total EMIs / net monthly income). My system prompt literally says "If you are not sure, say so. Do not invent...", and it invented anyway. Latency was 164 s on the first call (model loading into memory) and 47 s on the second (~1.5 tokens/s, likely CPU-only inference).
- **Design decision I made and why:** Prompts live in versioned files and the version is returned with every answer, so any output can be traced back to the exact prompt that produced it (audit rule 3). I also cut Spring AI's retries to 2 and mapped Ollama failures to clear 503/502 errors, so a missing model or a stopped Ollama fails fast instead of hanging for minutes.
- **What I'd do differently in production:** Never trust the model's own knowledge for domain facts: ground answers in our policy documents (RAG, POC 6) and keep all calculations in code (rule 1). Add an input hash and a persistent audit log for every call, run on a GPU or a hosted model with a latency SLA, and use evals to catch confident wrong answers like the FOIR one before users see them.

## POC 2: Structured extraction
- **What I built:** `POST /api/extract` turns salary-slip text into a validated `SalarySlip` record (BigDecimal money, `YYYY-MM` pay period, a list of deduction lines). Spring AI's `BeanOutputConverter` adds the JSON schema to the prompt, and Bean Validation plus cross-field checks (gross - deductions = net, the lines add up to the printed total) catch output that parses but is wrong. Each response carries the model, prompt version, input SHA-256, tokens and latency. I also wrote a Python generator for 10 synthetic slips, each with a trap (YTD column, bilingual labels, OCR noise, `Mar'26`, paise, no printed total), and an eval script that scores the model against `expected.json`.
- **What I learned:** Structured output is a prompt plus a parser, not a guarantee. The schema is just more text the model reads, and `@JsonPropertyDescription` works as a per-field instruction. "Parsed fine" and "correct" are different things: the type system catches format problems, but only domain checks like gross - deductions = net catch a wrong number in the right shape. Evals turn "seems to work" into a score you can compare across prompt versions (v1: 9/10, v2: 10/10).
- **What surprised me / what broke:** Slip-09 prints no total deductions. Prompt v1 asked for the total anyway, so the model "added" 1,800 + 200 + 9,150 and got 19,700 instead of 11,150, then wrote it down confidently. The consistency check flagged it as invalid. My very first eval run returned only 2 of the 6 fields and still reported `valid: true`, so a passing validator doesn't prove the extraction is complete. Latency was about 70–120 s per slip on CPU, and v2 roughly doubled the completion tokens (about 80 to about 155) because the model now writes out each deduction line.
- **Design decision I made and why:** The model copies and Java calculates (rule 1). In v2 the model lists every deduction line and returns null when the slip has no printed total, and `SalarySlip.withComputedTotals()` does the sum. I call `BeanOutputConverter` directly instead of `.entity()` so the raw model output survives a parse failure, because that output is what you debug. Extraction runs with a fixed temperature and seed so eval runs are repeatable. I don't extract PAN or account numbers (data minimisation), and INFO logs never contain slip content.
- **What I'd do differently in production:** Mask PII before the LLM call (rule 2): right now the full slip, PAN included, goes to the model, which is only acceptable because it's local and the data is synthetic. Write a persistent audit record for every call (rule 3). Try Ollama's native JSON-schema mode or a stronger model to cut format failures. Retry once on invalid output, with the validation errors fed back, before sending the slip to a human review queue. Run the eval suite in CI on every prompt change, with many more slips, including real-world layouts.
