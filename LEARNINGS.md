## POC 1: Talk to a local LLM from Java
- **What I built:** Spring Boot 4.1 + Spring AI 2.0 + Ollama (`qwen2.5:7b`) with `GET/POST /api/ask`. The system prompt is loaded from a versioned file (`prompts/banking-assistant-v1.st`), temperature and system prompt can be overridden per request, and every response returns model, prompt version, temperature, prompt/completion tokens and latency. A unit test with a fake `ChatModel` checks what Spring AI sends, with no Ollama needed.
- **What I learned:** Temperature reshapes token probabilities; it does not make output deterministic. The model still samples, so the same question at 0.2 gave two differently worded answers (172 prompt tokens both times, 79 vs 72 completion tokens). The system prompt is just more tokens in the context: it steers the model, it doesn't enforce anything.
- **What surprised me / what broke:** Asked "What is FOIR?", the model said "Fixed Operational Interest Rate" twice, confidently. That's wrong: it is Fixed Obligation to Income Ratio (total EMIs / net monthly income). My system prompt literally says "If you are not sure, say so. Do not invent...", and it invented anyway. Latency was 164 s on the first call (model loading into memory) and 47 s on the second (~1.5 tokens/s, likely CPU-only inference).
- **Design decision I made and why:** Prompts live in versioned files and the version is returned with every answer, so any output can be traced back to the exact prompt that produced it (audit rule 3). I also cut Spring AI's retries to 2 and mapped Ollama failures to clear 503/502 errors, so a missing model or a stopped Ollama fails fast instead of hanging for minutes.
- **What I'd do differently in production:** Never trust the model's own knowledge for domain facts: ground answers in our policy documents (RAG, POC 6) and keep all calculations in code (rule 1). Add an input hash and a persistent audit log for every call, run on a GPU or a hosted model with a latency SLA, and use evals to catch confident wrong answers like the FOIR one before users see them.

## POC 2: Structured extraction
- **What I built:** `POST /api/extract` turns salary-slip text into a validated `SalarySlip` record (BigDecimal money, `YYYY-MM` pay period, a list of deduction lines). Spring AI's `BeanOutputConverter` adds the JSON schema to the prompt, and Bean Validation plus cross-field checks (gross - deductions = net, the lines add up to the printed total) catch output that parses but is wrong. Each response carries the model, prompt version, input SHA-256, tokens and latency. I also wrote a Python generator for 10 synthetic slips, each with a trap (YTD column, bilingual labels, OCR noise, `Mar'26`, paise, no printed total), and an eval script that scores the model against `expected.json`.
- **What I learned:** Structured output is a prompt plus a parser, not a guarantee. The schema is just more text the model reads, and `@JsonPropertyDescription` works as a per-field instruction. "Parsed fine" and "correct" are different things: the type system catches format problems, but only domain checks like gross - deductions = net catch a wrong number in the right shape. Evals turn "seems to work" into a score you can compare across prompt versions (v1: 9/10, v2: 10/10).
- **What surprised me / what broke:** Slip-09 prints no total deductions. Prompt v1 asked for the total anyway, so the model "added" 1,800 + 200 + 9,150 and got 19,700 instead of 11,150, then wrote it down confidently. The consistency check flagged it as invalid. My very first eval run returned only 2 of the 6 fields and still reported `valid: true`, so a passing validator doesn't prove the extraction is complete. Latency was about 70–120 s per slip on CPU, and v2 roughly doubled the completion tokens (about 80 to about 155) because the model now writes out each deduction line.
- **Design decision I made and why:** The model copies and Java calculates (rule 1). In v2 the model lists every deduction line and returns null when the slip has no printed total, and `SalarySlip.withComputedTotals()` does the sum. I call `BeanOutputConverter` directly instead of `.entity()` so the raw model output survives a parse failure, because that output is what you debug. Extraction runs with a fixed temperature and seed so eval runs are repeatable. I don't extract PAN or account numbers (data minimisation), and INFO logs never contain slip content.
- **What I'd do differently in production:** Mask PII before the LLM call (rule 2): right now the full slip, PAN included, goes to the model, which is only acceptable because it's local and the data is synthetic. Write a persistent audit record for every call (rule 3). Try Ollama's native JSON-schema mode or a stronger model to cut format failures. Retry once on invalid output, with the validation errors fed back, before sending the slip to a human review queue. Run the eval suite in CI on every prompt change, with many more slips, including real-world layouts.

## POC 3: Tool calling
- **What I built:** `/api/advise`, an agent loop in which the LLM turns a free-text question into tool requests, Java runs the tools, and the LLM explains the results. There are two tools on `LoanTools`: `calculateEmi` (BigDecimal, validated inputs) and a mock `getCibilScore` that reads synthetic data for three applicants: Priya (happy path), Rahul (low score) and Arjun (no credit history). A `RecordingToolCallback` wraps each tool, so every response lists the tool calls with their arguments, results and timing. "Can Priya afford 5 lakh for 3 years at 12%?" called both tools and got ₹16,607 and 762.
- **What I learned:** The LLM never calls Java. It replies with a tool *request*, and Spring AI's loop decides to run it, so Java validates the arguments and controls what each tool can see. The model only sees the tool name, its description and the parameter schema, which makes tool descriptions a form of prompt engineering. Each tool round-trip is another LLM call. Tools make the LLM accurate; they don't make it necessary. Typed input belongs on a typed endpoint that calls Java directly, and the LLM is only for the natural-language edges.
- **What surprised me / what broke:** With prompt v1, the Priya question called only `calculateEmi` and skipped the credit score, even though the tool description said to use it for "ability to borrow". The line "don't judge affordability" probably pulled the model away from it. Prompt v2 added an explicit rule that affordability questions need both tools, and both then ran. Separately, Spring AI refuses to call a tool method that takes `ToolContext` when the context is empty, so a plain question with no `applicantId` would have crashed `getCibilScore`. A unit test caught it before any real call did. The answer also called 762 "a good score", an opinion the tools never gave. The full loop took 127 s, compared with about 10 ms for the two Java calls.
- **Design decision I made and why:** The tools return facts (EMI, score, status) and never verdicts like "affordable" or "approved", so the LLM can only explain what Java produced (rule 1). `getCibilScore` takes a name or a code-supplied `applicantId` through `ToolContext` instead of a PAN, so the model never sees or produces a PAN (rule 2). Missing data comes back as an explicit status (`NO_CREDIT_HISTORY`, `NOT_FOUND`) with a sentence the model can repeat, not an exception it might paraphrase into a guess. Every tool call is recorded in the response (rule 3).
- **What I'd do differently in production:** Keep the LLM off the decision path altogether: the loan flow becomes a deterministic Java pipeline (POC 7), and tool calling serves only the officer's ad-hoc questions. Add a prompt-level or output check against opinions like "good score", and run a small eval set of questions with their expected tool calls on every prompt change, since v1 vs v2 showed that one line changes tool selection. Persist the tool-call records to the audit log, cap the number of tool iterations per request, and use a GPU or hosted model, since three LLM calls on CPU take about 2 minutes.

## POC 4: First MCP server
- **What I built:** `mcp-credit-bureau`, a separate Spring Boot service on port 8082 that publishes `getCreditReport` over MCP (Streamable HTTP at `/mcp`). It has no LLM of its own and only publishes tools. The data is synthetic for 5 applicants (score, active accounts, existing EMI, 90+ DPD, enquiries). Tests cover the tool in plain Java and a real MCP client talking to the server over HTTP. Both done-when clients called it: MCP Inspector (`tools/list`, then `tools/call` for found, no-history and not-found) and Claude Code, which fetched Priya's and APP-003's reports.
- **What I learned:** MCP is a contract for AI tools, the way OpenAPI is for REST. The protocol is small JSON-RPC: `initialize` (server name, capabilities, instructions and a session id) → `tools/list` (name, description, JSON schema) → `tools/call`. `@McpTool` is POC 3's `@Tool` moved behind a network boundary: one owning service, many clients, no shared code. The server never sees the client's LLM, and the client never sees the server's code. Each side only sees the schema and the JSON.
- **What surprised me / what broke:** Very little code is needed: one annotation publishes the tool, and the default config already serves Streamable HTTP at `/mcp`. Two clients from different vendors (Inspector, Claude Code) worked first time against the same endpoint. The scary part is how easily data leaves: once Claude Code is connected, everything the tool returns goes to a cloud LLM, so the tool's *output* design is a security decision. Claude Code also read and followed the server's instructions, saying "facts only, not an approval" without being asked.
- **Design decision I made and why:** Lookup is by applicant id or name, never by PAN, because in POC 5 an LLM fills these arguments (rule 2). The tool returns a dedicated `CreditReport` record, not the internal `BureauRecord`, so there's no PAN, no name and no verdict field (rules 1 and 2). `NOT_FOUND` and `NO_CREDIT_HISTORY` are explicit statuses, because "unknown person" and "known person with no history" mean different things to a lender. The tool is marked read-only and idempotent, so clients know it's safe to call or retry. The server binds to 127.0.0.1 because it has no auth.
- **What I'd do differently in production:** Add authentication (OAuth per the MCP spec) and authorisation per client: an internal orchestrator might see more fields than a developer's Claude Code. Write an audit log for every `tools/call` (who, which applicant, when), apply rate limits, and give the bureau tool a stable versioned contract, since renaming a field breaks every client's prompts. Real bureau lookups would be keyed by PAN on the server side only, resolved from an applicant id the bank already holds.

## POC 5: MCP client
- **What I built:** The orchestrator now gets credit data from `mcp-credit-bureau` over MCP instead of a local `@Tool`. Adding the `spring-ai-starter-mcp-client` dependency plus a URL in config was enough to discover `getCreditReport`, and `AdviseService` offers it to the model next to the local `calculateEmi`. The local `getCibilScore` and the orchestrator's copy of applicant data are deleted, so the bureau owns that data now. POC 3's question passed again: `calculateEmi` ran locally (₹16,607) and `getCreditReport` ran over HTTP (762), with the same request id in both services' logs.
- **What I learned:** To the model, a remote tool and a local tool are identical: both are a name, a description and a schema. The difference is all operational: network latency (≈90 ms vs ≈10 ms, which is nothing next to ~75–170 s of LLM time), failure modes, and who owns the data. The calling service can pass data to the server out of band. Spring AI turns the `ToolContext` into the MCP request's `_meta`, which the server reads with an `McpMeta` parameter that never appears in the tool schema. That gave me a trusted `applicantId` and cross-service tracing without the LLM ever touching them.
- **What surprised me / what broke:** (1) The model **invented an applicant name**, "Rajiv", when the question said "this applicant" and code supplied the id. The data was still right, because the trusted `_meta` id wins at the bureau, but the answer named the wrong person. Adding "never guess a name" to the tool description changed nothing at temperature 0. What worked was giving the model the real id, so it had nothing to invent. (2) When the bureau was down at the first request, the model returned **empty text**, which reproduced directly against Ollama. The fix is a code guard that replaces a blank answer with an explicit "bureau unavailable" message. (3) A dead bureau fails in **two different places**: at discovery (no tools listed yet) or at call time (the MCP client had cached the tool list). I had only designed for the first, and only the live test showed the second.
- **Design decision I made and why:** Local tools for maths, remote tools over MCP for data another domain owns. The MCP client connects lazily (`initialized=false`) and remote tools are fetched on every request, so the orchestrator starts without the bureau, keeps working with local tools when it's down, and picks it up again with no restart. That's the same resilience I'd expect between any two microservices. The response records `remoteToolsError` and per-call errors, so an "I can't get the score" answer can always be traced to its cause (rule 3).
- **What I'd do differently in production:** Authenticate the MCP connection (OAuth) and only trust `_meta` from authenticated services. Add timeouts, a circuit breaker and metrics around remote tools. Filter which remote tools each use case may see (Spring AI has `McpToolFilter`), so a new tool on the bureau doesn't silently appear in every agent. Pin the bureau's tool contract with a version, run the eval set whenever either side changes, and treat "the model invented an argument" as a class of bug to test for, not a one-off.

## POC 6: RAG over credit policy
- **What I built:** A synthetic 30-clause credit policy in `policy-docs/`, chunked one clause per chunk (with a chapter breadcrumb), embedded with `nomic-embed-text` (768 numbers) and stored in a local Qdrant (Windows binary, no Docker). `/api/policy/ask` embeds the question, retrieves the 3 nearest clauses, and the LLM answers from those clauses only, citing §. `/api/policy/search` does retrieval alone in ~0.1 s, which made tuning fast. A 16-question eval scores retrieval (hit@1 77%, hit@3 100%) and answers (v1 15/16, v2 16/16). "What is the maximum FOIR?" now returns 50% (§4.2) and 45% (§4.3); without RAG the same model still says "Fixed Operational Interest Rate, 9% to 14%".
- **What I learned:** An embedding is meaning as numbers, so "salary towards EMIs" can find the FOIR clause with no shared words, but only just (third place, 0.557). Similarity scores are relative and compressed: correct clauses score 0.70–0.83, off-topic "cryptocurrency" still scores 0.58, and only truly unrelated text falls under 0.5. So a threshold can stop nonsense but can't decide what's in scope; the grounding prompt has to. top-k > 1 matters because the LLM re-ranks: retrieval put the right clause third for three questions and the model still picked it. Chunking is the biggest lever: clause chunks hit 100% at k=3, fixed 500-char chunks 92%, and each fixed chunk mixed 3–4 clauses, so its "hits" were vaguer than they looked.
- **What surprised me / what broke:** (1) The failure wasn't retrieval but attribution: for "is a bounced EMI a problem?" the model stated the §4.8 rule but cited §2.4, the definition of bounce. My citation guard passed it, because §2.4 was retrieved; a guard can check that a citation exists, not that it supports the sentence. Prompt v2 (cite the clause whose own text you rely on; definitions vs rules) fixed it with no regressions. (2) nomic's documented `search_query:`/`search_document:` prefixes fixed the paraphrase but cut the §4.2-vs-§4.3 margin to 0.001 and shifted every score up, so they're a trade-off to measure, not a default. (3) An "encoding bug" (§ shown as Â§) was my Windows Python pipe decoding UTF-8 as cp1252; the API bytes were correct. Check the raw bytes before fixing code.
- **Design decision I made and why:** Retrieval is explicit in `PolicyService`, not hidden in Spring AI's `QuestionAnswerAdvisor`, so the retrieved clauses and scores are returned (rule 3), code can refuse before any LLM call when nothing is similar enough, and code can check citations against what was retrieved. Clause chunking because a clause is the unit an officer cites and is never cut in half. Re-ingest deletes the document's old chunks and uses name-based UUIDs, so it is idempotent. The Qdrant collection is created on first ingest (`initialize-schema=false`), so the app starts and POC 1–5 work without Qdrant, returns a clear 503 for policy calls, and recovers when Qdrant comes back. Live applicant data stays on MCP (rule 4): asked for Priya's score, RAG answers that the policy doesn't cover it.
- **What I'd do differently in production:** Version the index with the policy (doc id + effective date in metadata, filter by the version in force on the application date), and re-ingest from a pipeline when the document changes. Add a citation-support check (does the cited clause actually contain the claimed number?) instead of trusting the prompt alone, and use hybrid search (keyword + vector) so exact terms like "§4.8" or "FOIR" can't be outranked. Grow the eval set from real officer questions, run it on every prompt, chunking or embedding-model change, and remember that changing the embedding model means re-embedding everything.

## POC 7: Decision engine + application workflow
- **What I built:** `POST /api/applications` takes Priya from application to credit memo in one call: BUREAU (`getCreditReport` over MCP, called by code) → INCOME (LLM extracts 3 salary slips, validation checks them, average net pay) → DECIDE (`DecisionEngine`, pure Java, every rule tied to a policy §) → POLICY (clause text looked up by section) → MEMO (LLM explains; code checks the memo states the engine's outcome and cites only provided sections). The response carries the decision with every check (PASS / FAIL / REFER / NOT_CHECKED, actual vs limit), the facts, the memo, the memo check and a per-step trace. 28 new tests (18 rules incl. every boundary, 11 workflow with a fake bureau and fake LLM). Live: 11/11 checks correct (incl. FOIR 50.4% → REJECT, unknown applicant → REFER, bureau down → 503, bad input → 400): 5/5 decisions and memos in fast mode, the full 3-slip Priya run (APPROVE, FOIR 43.1%, 549 s: 409 s reading slips, 140 s memo, 2 ms deciding) and the duplicate-month case (REFER, engine skipped, no memo LLM call).
- **What I learned:** The decision is the cheap, easy, exact part: the rules run in ~5 ms and the 18 tests prove them, boundaries included (FOIR exactly 50.0% passes, 50.04% fails though it displays as "50.0%"). Everything slow and uncertain is the LLM at the edges: reading slips (~2 min each) and writing the memo (~3–4 min). A fixed workflow beats an agent here because every application needs the same facts in the same order; nothing is left for the model to choose, so nothing can be skipped or invented. And "lookup vs search": POC 6 needed vector search because the question didn't name a clause, but here the code knows FOIR is §4.2, so it looks it up, with no Qdrant needed.
- **What surprised me / what broke:** (1) Memo v1 wrote "PASS §4.8: no bounces" when bounces were NOT_CHECKED (no bank statements). The model turned "not verified" into "passed", which is the most dangerous mistake a credit memo can make. v2 (passed rules as § numbers only, clause text only for failed/referred rules) fixed it and cut the memo from 408 s to ~200 s (1,784 → 1,149 prompt tokens). (2) The memo check passes memos that are still incomplete or overstated: Sneha's memo omits her 11% rate, two memos say "meeting all policy criteria" while 4 checks are unverified, and §4.8 appears as both passed (DPD) and not verified (bounces) because one clause holds two rules. Code can check the outcome and citations; it can't yet check omissions or claims. (3) A test I expected to fail on tenure (11 months) also failed FOIR, because the engine runs every rule. That was correct behaviour; the test was wrong.
- **Design decision I made and why:** Facts before rules: an invalid slip, a repeated pay month or mismatched names give REFER, the engine doesn't run, and code writes the memo, so rules never run on numbers we don't trust. Every rule always runs (no early return), so a rejection lists every reason. NOT_CHECKED is an explicit status, never counted as passed. The bureau is called first, so an outage fails in under a second as a 503 (a technical error, never a credit outcome). One EMI formula (`EmiCalculator`) shared by the engine and the POC 3 tool, and every limit lives in `PolicyLimits` next to its §. The memo input has the applicant id only, no name or PAN.
- **What I'd do differently in production:** Persist each decision with its rules version and policy version so it can be replayed. Load limits from a versioned policy config owned by credit risk, not Java constants. Add the missing data sources (bank statements for bounces and salary credits, KYC for age) so NOT_CHECKED rules get decided. Add a faithfulness check on the memo (every figure in the memo must match the decision; every unverified rule must be mentioned as such; no "meets all criteria" when anything is NOT_CHECKED). That's POC 8. Run extraction on a GPU or hosted model; the full flow is ~9 minutes on CPU.

## POC 8: Guardrails + evals
- **What I built:** `LlmGuardAdvisor`, one Spring AI advisor registered on every `ChatClient` through a `ChatClientCustomizer`: it masks PAN, Aadhaar, account numbers, phones and emails before the call and writes one append-only audit record after it (purpose, model, prompt version, SHA-256 of the masked input, output, tokens, latency, PII counts; fail closed). `MemoFaithfulness` checks every memo in code: every number must come from the memo input, the key figures must be there, NOT_CHECKED sections must be disclosed, failed ones cited, no "all passed" claims. A golden set of 20 synthetic applicants (each on one rule boundary: FOIR exactly 50% vs 50.002%, CIBIL 700, 4 vs 5 enquiries, thin file, self-employed 45%) plus bad-document cases, with an answer key verified by a second, independent Python implementation of the policy. Result on the full run (21 of 22 cases, 2 h 38 min on CPU): extraction 60/60, decision 21/21, consistency 21/21, faithfulness 19/19, PII masked 60/60, audited 79/79. 94 tests.
- **What I learned:** An eval is only as good as its answer key. Generating expected outcomes with an independent implementation (not by running the Java engine) is what makes "decision 100%" mean something. Boundary cases are where the bugs live, so every golden-set applicant sits on one. Putting the guard in one advisor instead of in each service means rule 2 and rule 3 hold for services that don't exist yet. And faithfulness can mostly be checked by code: "is every number in the memo in the input?" catches invented figures without a second LLM.
- **What surprised me / what broke:** The memo kept overclaiming. v3 said "never write meets all criteria" and the model still wrote "all criteria". v4 offered two sentences, one for "has failures" and one for "no failures", and the model blended them into "recommends APPROVE because all checks passed". Negative instructions and conditional choices don't work reliably on a 7B model. v5 moved the choice into code (`summaryOpening()`) and the model just copies the sentence: 19/19 faithful. Also: a 3-hour eval on a 16 GB laptop gets killed by memory pressure, so the runner writes the report after every case. That saved the 21 results when the last case was killed.
- **Design decision I made and why:** Mask one-way (no token map), because nothing we ask the LLM needs the originals back. Store the input's hash, not the input, so the audit log doesn't become a second copy of customer data. Fail closed: if the audit write fails, the LLM output is not used. Faithfulness by deterministic code, not LLM-as-judge: free, repeatable, runs on every memo in production, not just in evals. Names aren't masked yet, because the workflow compares names across slips.
- **What I'd do differently in production:** Mask embedding calls too (they bypass `ChatClient` today). Replace regex with an NER-based detector plus a test corpus of real document layouts (a PAN split across lines slips through). Move the audit log to a database table with retention and access control (it holds model outputs about applicants). Run the golden set in CI on every prompt or model change, with thresholds that block the merge. Add an LLM-as-judge only for what code can't see (tone, a right number next to the wrong label), and evaluate the judge too.
